PDF Extraction Pipeline

PDFs land in S3, a queue absorbs bursts and retries, and one Rust Lambda per document writes structured JSON and Markdown to a separate bucket.

Validated on LocalStack only. The Pulumi stack in infra/ deploys this design and passes the end-to-end test. The dead-letter transition, X-Ray and a real AWS deployment are not yet exercised.

Settings the stack must apply

S3 → SQSNotification for ObjectCreated on prefix raw/, suffix .pdf, plus a queue policy that lets the bucket send messages.
Output bucketSeparate bucket from the input, so writing results can never re-trigger the pipeline.
QueueVisibility timeout of at least 6× the Lambda timeout. Redrive to the DLQ after 3 receives.
Event source mappingBatch size 1, so memory use follows one PDF. A MaximumConcurrency cap keeps a bulk upload from flooding downstream systems.
Lambdaarm64, provided.al2023, memory sized from the Max Memory Used line in the REPORT log, X-Ray active tracing on. Environment: OUTPUT_BUCKET, OUTPUT_PREFIX, MAX_PDF_BYTES.
IAMRead on the raw bucket, write on the output bucket, receive/delete on the queue, log writes, X-Ray write. Nothing broader.
AlarmsMessages in the DLQ, Failures, PagesFailed, and PagesScanned (pages that need OCR).
